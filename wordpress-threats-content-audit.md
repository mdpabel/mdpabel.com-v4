# WordPress Threats Content and SEO Audit

Audit date: 2026-07-22

Scope: all 39 Markdown entries and six review sidecars in `src/content/wordpress-threats/`; all 85 referenced screenshots; the root `sitemap.xml`; local blog, case-study, guide, malware-log, fake-plugin, and service-page sources; and the relevant collection schemas, routes, templates, related-content logic, structured data, sitemap/RSS generation, and image handling.

No threat draft was edited. “Indexable” below is the recommended eventual state after the stated evidence, privacy, editorial, and implementation gates pass; none of these drafts is currently public because the `wordpress-threats` collection has no page route and is absent from the generated sitemap and RSS feed.

## Executive findings

- The collection is not currently publishable as implemented. `src/content.config.ts` and the duplicate `src/content/config.ts` retain `vtLink` and `vtScore`; the prohibition on VirusTotal material requires deleting those schema fields and every related frontmatter/body reference before publication.
- All 85 screenshot references use `/images/wordpress-threats/...`, but the files are in `public/wordpress-threats/...`. Every current screenshot URL therefore misses its real public path. Several images also expose client identifiers, account paths, email addresses, or database details and must not be published without irreversible redaction or cropping.
- The drafts contain 73 VirusTotal mentions and 63 “zero-day” mentions. These are not supported by repository evidence. Several drafts also call an infection a WordPress vulnerability or exploit without identifying a vulnerable component and affected version.
- Existing public content already owns much of the broad search intent: detection/removal guides, commercial removal pages, client recovery case studies, hidden-admin guidance, cron persistence, `.htaccess` cleanup, JavaScript infection, database spam, and fake-plugin lists. Research entries should document a narrowly defined artifact or behavior and link to those pages instead of retargeting their queries.
- The shared `ArticlePage.astro` uses `BlogPosting` only for blog posts and generic `Article` for other types. Related items for case studies, guides, and malware logs are the first three fetched entries rather than semantically matched entries. A research route needs evidence-aware related-content matching and `TechArticle` or carefully scoped `Article` structured data.
- Full malicious samples should remain in the private evidence archive. Public pages should show only the smallest inert excerpt needed to substantiate a finding, with credentials removed, domains defanged, long encoded payloads omitted, and no repaired or completed code.

## 1. Recommended information architecture

### Content roles and URL ownership

Keep the existing public roles explicit:

- `/blog/`: broad problem recognition, detection, remediation, and prevention. These pages own general “how to detect/remove/fix” queries.
- `/case-studies/`: complete, anonymized incident narratives with starting condition, investigation, recovery work, and outcome.
- Service pages such as `/wordpress-malware-removal/`, `/fake-captcha-malware-removal/`, and `/remove-japanese-seo-spam/`: commercial and conversion intent.
- `/malware-research/`: a new evidence-led collection for one specific malicious artifact, code pattern, persistence mechanism, or observable behavior. A page qualifies only when the evidence can sustain a unique finding, reproducible identifiers, meaningful analyst interpretation, and a useful distinction from an existing page.
- `/malware-log/`: shorter, consistently formatted observations. Use this for a single path/signature, incomplete behavior chain, evidence appendix to an existing guide, or incident-specific example that does not justify a long page.
- `/fake-wordpress-plugins/`: retain as the specialized artifact database for fake-plugin identities. Substantial fake-plugin entries can use its existing URL family rather than duplicating them under `/malware-research/`.
- Archive: private evidence that is duplicated, unsafe, inadequately supported, or not yet attributable. Archived material must not be routed, indexed, placed in a public feed, or used as structured-data claims.

### Proposed route and collection behavior

1. Add a dedicated `/malware-research/[slug]/` route only when the first approved batch is ready. Do not expose the current drafts simply by adding a catch-all route.
2. Build a `/malware-research/` hub that explains methodology, evidence/confidence labels, privacy/redaction practices, and the distinction between observed artifacts and vulnerability research.
3. Keep short entries in the current WordPress-backed `/malware-log/[slug]/` system or migrate both sources to one normalized content model. Avoid two independent malware-log stores with different fields.
4. Exclude `draft`, `review`, `archived`, merged, and intentionally non-indexable evidence appendices from the sitemap and RSS. The current `sitemap.xml.ts` and `rss.xml.ts` do not read `wordpress-threats`; any future inclusion must filter explicitly by publication and robots status.
5. Use one canonical URL per artifact. Merged drafts must resolve to the surviving page rather than produce near-duplicate pages. Do not create redirect routes for drafts that were never public.
6. Add breadcrumbs: Home → Malware Research → Entry, or Home → Fake WordPress Plugins → Entry. Logs retain Home → Malware Log → Entry.
7. Add a visible “Evidence status” panel to research pages: what was observed, what the analyst assesses, and what this evidence does not establish.

### Internal-linking model

Each research/log page should link according to user need, not keyword repetition:

- Upward to one broad guide that explains detection or cleanup of that artifact class.
- To one relevant case study only when it supplies a fuller recovery narrative or is demonstrably the same anonymized incident.
- To the relevant commercial service as a restrained next step, never as the page’s primary purpose.
- Laterally to no more than three genuinely related artifacts matched on structured fields such as artifact family, file location, persistence method, or behavior—not simply the first three fetched entries.
- Back from the broad guide or case study to the research page with wording such as “See the code-level artifact analysis,” so the research page deepens the topic rather than competing with the guide.

The existing `ArticlePage.astro` currently selects the first three case studies, guides, or malware logs as related items. Replace that behavior for research content with scored matching: exact artifact/family first, then behavior, location, and content role; exclude the current entry and merged/noindex items.

### Template, metadata, and structured-data requirements

- Use a research-specific template instead of treating entries as generic WordPress posts. It should render evidence findings, confidence labels, code excerpts, screenshots/figures, limitations, related public guidance, and privacy-safe indicators predictably.
- Emit `TechArticle` for substantive technical research only when the visible article supports that classification. Use `Article` for concise malware logs. Include `WebPage`, `BreadcrumbList`, and reviewed `ImageObject` nodes where appropriate.
- Do not emit claims, dates, hashes, severity, affected software, or author conclusions in JSON-LD unless the same statements are visible and verified in the page.
- Keep canonical, Open Graph, Twitter, `robots`, publication date, and modification date behavior from `NewLayout.astro`, but make `noindex` a first-class content field rather than an ad hoc template option.
- Do not auto-generate `FAQPage` from incidental headings. Only emit FAQ schema for a visible, intentionally curated FAQ section whose answers are present on the page.
- Replace generic metadata. Descriptions should identify the observed artifact and the evidence boundary in plain language; they should not use “zero-day,” “critical vulnerability,” “complete removal,” or marketing superlatives.

## 4. Writing and factual-verification rules

### Required article structure

Use a consistent evidence-led order:

1. Scope and evidence available
2. Confirmed findings
3. Observed artifact and location
4. Defensive code analysis using minimal inert excerpts
5. Analyst assessment
6. What this evidence does not establish
7. Detection pivots and safe investigation notes
8. Relationship to the broader guide, case study, and service
9. Evidence limitations and privacy/redaction note

### Factual controls

- Delete every VirusTotal field, score, badge, description, and link from frontmatter, body copy, components, and structured data.
- Never use “zero-day” for these samples. None of the repository evidence documents and verifies a previously unknown vulnerability.
- Do not call an infection, injected file, backdoor, fake plugin, or malicious database record a WordPress vulnerability. Name a vulnerable component and affected version only when direct evidence establishes both.
- Do not infer initial access from the location of malware. A file under a plugin directory does not prove that plugin was vulnerable, and an MU plugin does not identify how it arrived.
- State evidence at the narrowest supported level: “the supplied code contains,” “the screenshot shows,” or “in this incident/query.” Avoid “this malware always,” “sites are affected,” and campaign-wide language.
- Keep confirmed findings and analyst assessment visibly separate. Every page must also contain a “Not established by this evidence” section.
- Do not invent behavior from obfuscation alone. Decode or trace only as needed for defensive analysis in a controlled review; do not execute samples, repair code, fill missing stages, or publish an operational reconstruction.
- Do not equate local credential logging with network exfiltration. Do not call data “stolen” from a client unless collection/transfer and affected records are documented in privacy-safe evidence.
- Do not claim persistence merely because a malicious file exists. Name the verified loading, restoration, scheduled task, account, autoload, or self-copy mechanism.
- Treat UI discrepancies as symptoms. A mismatched user count can corroborate hiding code but does not independently prove a hidden user.
- Treat scanner labels and HTTP error pages as context. The underlying file/code/database/configuration evidence must support the technical finding.
- Do not use dates as first-seen/discovery dates unless case notes explicitly establish them. Do not invent affected versions, hashes, prevalence, client outcomes, traffic, search volume, or ranking difficulty.
- Defang necessary indicators and remove unnecessary live domains. Never publish client domains, credentials, usernames, emails, database values, filesystem account paths, or personal data.
- Use precise malware terms: loader for code that loads another value/stage; dropper only when it writes a payload; credential logger when it records credentials; redirect injector when redirect logic is shown; web shell when an interactive command/file-management interface or code is verified; persistence only when a reloading/restoration mechanism is verified.

### Code handling

- Preserve the original sample and its verified digest in a private evidence system, not in the public content repository when client confidentiality or operational risk applies.
- Public excerpts should be the smallest fragment required to show a hook, conditional, decoder shape, file write, include, redirect, or remote request. Replace credentials, tokens, paths, and payload bodies with explicit redaction markers.
- Short configuration rules such as a `.htaccess` `FilesMatch` block can usually be preserved because they are evidence and not a complete malicious program. Long encoded blobs, web shells, credential stealers, user-creation credentials, bypass modules, and deployers must be shortened or omitted.
- Do not complete truncated code, correct syntax, expose a working request recipe, derive a usable payload, or improve reliability. Pseudocode and a defensive control-flow description are preferable when an excerpt would remain operational.
- Clearly label excerpts “redacted” and identify which finding they support. Never imply the excerpt is the whole sample.

### SEO controls

- One page, one artifact-level intent. Titles should name the distinctive file, plugin, marker, storage location, or behavior rather than reuse “WordPress malware removal,” “how to fix,” or “complete guide.”
- Do not target broad removal phrases on research pages. Link to the established guide/service for cleanup steps.
- Write descriptions around the evidence: what was found, where, and what the analysis confirms. Avoid generic urgency and unsupported severity.
- Use secondary phrases naturally as identifiers and synonyms, not as repetitive headings.
- Before publication, compare title, H1, description, outline, and internal anchors with the overlapping page listed in the table. If both pages answer the same task for the same reader, merge instead of attempting keyword differentiation.
